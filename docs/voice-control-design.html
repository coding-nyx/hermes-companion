Voice control + wake word for Hermes Companion

An always-listening wake-word service ("hey hermes") and a push-to-talk dictation path, wired into the same gateway proxy and Hermes webhook plumbing that already carries notifications and OTP replies.

Wake-word on-device only Reuses ActiveGatewayConfig pattern Same webhook bus as notification-otp-reply Battery budget ~7 mAh/hour

01Overview

Key numbers and architectural shape at a glance.

Wake-word latency ~180 ms From "hermes" phoneme to capture-service start, on Pixel-class hardware with Porcupine.
TTS engines 2 Android TextToSpeech (default, free, on-device) + MiniMax TTS (opt-in, already pooled) + Grok TTS (fallback) + ElevenLabs (premium).
STT engines 2 Android SpeechRecognizer (default) + Whisper-tiny on-device (opt-in).
Privacy tier Local-first Wake-word detection, raw audio, and idle state never leave the device.
Constraint, hard. Wake-word spotting is on-device only (Porcupine or openwakeword). No cloud round-trip. STT/TTS may route via the gateway for the reply side, but the mic path itself is local.

02Architecture

Single end-to-end path. The wake-word service and the capture service are separate Android foreground services that hand the mic between each other. Everything after STT funnels through the gateway proxy into upstream Hermes.

Solid cyan arrows are data flow. Dashed grey arrows are file/config reads.
:node Two foreground services WakeWordService owns idle mic. CaptureService owns active capture. They handoff via internal start commands — never both running.
gateway Proxy, no business logic Routes transcripts to upstream webhook, fans replies back to the correct companion session via voice_bus.
upstream Skill, not a route Same hermes webhook subscribe pattern as notification-otp-reply. Topic: voice.transcript.

03Two modes

Always-listen and push-to-talk share the back half (STT → gateway → upstream → TTS). They differ in how capture is triggered.

Always-listen ("hey hermes")

WakeWordService holds the mic with partial wake-lock. On detection it spawns CaptureService and hands off the mic. Re-acquires idle listening after the reply is spoken.

  • Trigger: wake-word acoustic match
  • Audio source: VOICE_RECOGNITION
  • CPU idle: ~3 mA on Pixel-class
  • False-positive brake: 5 hits in 10s → sleep 60s

Push-to-talk

CaptureService is started directly by the UI button (or a Bluetooth media-button intent). No wake-word loop runs. Capture ends when the user releases or silence is detected for 1.5s.

  • Trigger: hold FAB or BT media button
  • Capture ends on release or 1.5s silence
  • No persistent CPU cost
  • Default mode until wake-word is enabled
Mic handoff. Only one service holds AudioRecord at a time. WakeWordService releases the record before signaling CaptureService. WakeWordService resumes idle listen after TtsPlayer.onDone().

All gating happens in VoiceSettingsScreen on first toggle. Nothing is requested at install time.

Rationale copy. The settings screen shows: "Hermes needs the mic to hear 'hey hermes' even when the screen is off. Audio stays on this device unless you explicitly send a voice message."

06Audio focus strategy

Wake-word uses MediaRecorder.AudioSource.VOICE_RECOGNITION so Android's AEC and AGC are bypassed. TTS uses transient focus with may-duck.

Phone call Yield mic Audio focus loss stops capture immediately. Wake-word resumes when call ends.
Music playback Duck to 20% TTS ducked during reply; restored after. Wake-word capture unaffected.
Navigation prompt Queue TTS 1.5s Short delay then duck. Capture still works (mic is independent).
Other assistant active Accept ambiguity If "hey hermes" fires while Google Assistant is hot-worded, both respond. Documented behavior.

08Failure modes + recovery

Every external dependency can fail. Each one has a defined recovery path that doesn't require a human in the loop.

FailureDetectionRecovery
Wake-word model fails to loadWakeWordModel.load() throwsRestart service; after 3 fails, fall back to openwakeword; if still failing, disable wake-word + notify user.
Mic permission revokedSecurityException on AudioRecord.startStop service, deep-link to settings.
STT timeout (5s no speech)No final transcript emittedSend empty final; upstream replies "did you want to say something?"
Gateway offlineHTTP timeout or 5xxQueue transcript locally, retry with exponential backoff; surface "offline — saved" toast.
TTS engine crashesTextToSpeech.onErrorFall back to next provider in priority list: Android -> MiniMax -> Grok -> ElevenLabs. If all fail, show reply as on-screen text.
Wake-word false-positive storm5+ detections in 10sPause detector for 60s, log, alert user.
Battery critical (<15%)BatteryManager broadcastDisable wake-word automatically, notify user, restore when charged.

09Privacy posture

Raw audio never leaves the device. The mic path is local; only transcripts cross the gateway boundary.

Raw mic PCM during wake-wordyesnono
Raw mic PCM during capturedeleted after STTnono
Recognized transcript textnoyesyes
Detection events (count, no audio)local logopt metricsno
Hermes reply textyesyesoriginates
TTS audio (MiniMax / Grok / ElevenLabs)cachedyesoriginates
Voice config (engines, phrase)yesnono
Hard rule. Raw audio never leaves the device. The only thing that crosses the network is text (transcript → upstream, reply → downstream) or already-cached audio URLs (ElevenLabs replies). The companion app's NLS does not receive any audio; it only handles notifications.
